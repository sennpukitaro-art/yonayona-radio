# もじもじラジオの運営手順

## ひとりの回答カード

ホームの会話見本と同じお題に、120文字までの回答を入力し、1080×1080のPNG画像を作成・保存できる。対応端末では画像を共有でき、Xではお題とリンクを共有できる（画像は保存後に添付する）。画像の生成と回答の保持は端末内だけで行い、回答本文をサーバーや共有リンクへ送らない。

共有先は通常のホームの `?topic=free&utm_source=share#answerCard` などで、同じお題を表示する。友達招待とは別のリンクで、受け手を自動でマッチング待機・番組参加させない。回答カードの作成はMCの発言や会話番組の成立には数えない。共有リンクのGETは既存のpage_viewで計測されるが、カード作成件数や実人数は現在のログからは分からない。集客効果は未検証として扱う。

## 今回確かめること

対象の仮説は「声出しせず、友達1人とお題つきの文字雑談を試したい人」。ホームでは友達招待を先に案内し、知らない人とのランダム参加も選べるようにする。

最初の成果は、運営の動作確認を除いて、外部の2人が同じ番組でそれぞれ発言できたと確認すること。表示回数や投稿数だけで利用成功と判定しない。再利用したか・何が楽しかったか・どこで困ったかは、本人が感想を寄せた範囲で確認する。

## 反応への対応

1. 感想が届いた元のスレッドで、相手と内容を確かめる。
2. 感謝と、その感想に関係する実装済みの改善を一度伝える。未実装の機能を完了扱いしない。
3. 再試用は任意とし、相手が希望した場合だけ開始方法や日程を案内する。反応のない人へ繰り返し催促しない。
4. 招待機能は相手役を用意する機能ではない。2人目の参加意思が必要で、招待も公開番組・先着1名・作成から30分有効と説明する。
5. フィードバック、試用の承諾、実際の会話成立は別々に記録する。感想をくれた人数を参加確約人数として数えない。

## 集客の確認

紹介先ごとに `utm_source` を付ける。同じ7日間のログを取得し、重複する書き出しを混ぜずに既存の集計を実行する。

```sh
python3 scripts/summarize_metrics.py server.log > metrics.csv
```

| イベント | 意味 | 集計時の扱い |
|---|---|---|
| page_view | ホームへのGET要求 | 人数ではない。再読み込み、運営閲覧、ボットも含み得る |
| matching_attempt | ランダム参加や招待作成・参加の試行 | 再試行を含む。ユニーク人数として扱わない |
| matched_participant | ペアになった各MCの接続 | 1番組につき通常2件。人数・番組数を混同しない |
| conversation | MC2人がそれぞれ1回以上発言した番組 | 全流入元合計。これだけでは運営テストを除外できない |
| conversation_participant | 会話成立時の各MCの流入元 | 運営テストの照合に使う。2件を別々の番組として数えない |
| listener_join | リスナーとしての参加 | MC参加や会話成立と分けて見る |

動作確認用のURLには `?utm_source=internal` を付ける。`internal` を除いても、運営がタグなしで開いたアクセスやボットまでは除けない。流入元タグは自己申告の分類で、個人を識別するものではない。

`conversation` に流入元はない。会話成立を外部利用者の成果として報告する前に、同時刻・同じサーバーインスタンスの `conversation_participant` と、記録してあるテスト時刻を照合する。同時刻の番組が重なるなど判別できないものは「外部利用か不明」とする。外部と運営が混じった番組を、外部2人の会話と扱わない。

この計測には人を継続して識別する情報がないため、ユニーク利用者数・再訪率・人単位の参加率は算出できない。イベント件数の比率を人の転換率として発表しない。取得期間、ログの欠落やページ取得の残りがあれば、それも結果と一緒に記す。

1回の実験では、対象と伝える利用場面を固定して、日付・投稿先・投稿URL・反応・イベント件数を残す。件数が少ない場合は効果の断定を保留する。これは運営時に行う確認手順であり、自動の定期実行を設定するものではない。

## 告知と更新の前後

- 告知前にホームが開き、接続できることを確認する。無料サービスの休止後には起動待ちがあるため、読み込み中を正常表示と取り違えない。
- 通信処理を変更した更新では、ランダム参加と友達招待で2人が参加・送信できることを確認する。動作確認の時刻とタグを残し、集客成果から除く。
- 更新を反映する前に、放送中の番組とランダム待機者がいないことを確認する。招待待ちはこの一覧・待機人数に含まれないため、それだけで誰もいないと判定しない。
- 招待は30分で失効する。直近30分以内に参加開始が記録されている場合は招待待ちが残る可能性を確認し、利用中の更新を避ける。招待待ちを確かめられない場合は、最後の作成から期限が過ぎるまで反映を見送る。ログが欠けている場合も不在と断定しない。
- GitHubのブランチへのpushだけでは公開完了としない。実際に対象コミットのデプロイがliveになったこと、公開画面と参加操作が動くことを確認する。
- 更新後に接続・表示・エラーログを確認してから改善内容を告知する。実装やテスト完了を、利用者増加の証拠にはしない。

既存の開催時間は実際に決まったものだけ掲載する。新しい予定や参加確約を推測で作らない。
